# 代码审查最佳实践

> 进行有效代码审查的综合指南。

---

## 审查理念

### 代码审查的目标

**主要目标：**
- 在生产前捕捉 bug 和边界情况
- 确保代码可维护性和可读性
- 在团队中分享知识
- 一致地执行编码标准
- 改进设计和架构决策

**次要目标：**
- 指导初级开发者
- 建立团队文化和信任
- 通过讨论记录设计决策

### 代码审查不是什么

- 阻碍进度的把关机制
- 炫耀知识的机会
- 吹毛求疵格式的地方（用 linter）
- 重写为个人偏好的场合

---

## 沟通指南

### 语气和语言

**使用协作性语言：**
- "你觉得……怎么样" 而不是 "你应该……"
- "我们可否考虑……" 而不是 "这是错的"
- "我很好奇……" 而不是 "你为什么不……"

**具体且可操作：**
- 建议更改时包含代码示例
- 链接到文档或过去的讨论
- 解释建议背后的 "为什么"

### 处理分歧

1. **寻求理解**：先问澄清性问题
2. **承认有效观点**：表明你考虑了对方的观点
3. **提供数据**：使用基准测试、文档或示例
4. **必要时升级**：请高级开发者或架构师参与
5. **知道何时放手**：不是每个问题都值得争论

---

## 审查优先级

### 必须修复（阻断级）
- 安全漏洞
- 数据损坏风险
- 无迁移的破坏性变更
- 面向用户功能的错误处理缺失

### 应该修复（重要级）
- 测试覆盖缺口
- 中度性能问题
- 代码重复
- 不清晰的命名或结构
- 复杂逻辑缺少文档

### 最好有（非阻断）
- 超出 lint 范围的风格偏好
- 轻微优化
- 额外的测试用例
- 文档改进

---

## 应避免的反模式

### 审查者反模式

- **橡皮图章**：不实际审查就批准
- **吹毛求疵**：广泛争论琐碎细节
- **范围蔓延**："既然你在改，能不能也……"
- **幽灵**：要求更改后消失
- **完美主义**：因轻微风格偏好而阻断

### 提交者反模式

- **巨型 PR**：提交 1000+ 行变更
- **无上下文**：缺少 PR 描述或关联 issue
- **防御性回应**：争论每条建议
- **静默更新**：不做回应就更改代码

## 指标与改进

### 跟踪这些指标

- 首次审查时间
- 审查周期时间
- 审查轮数
- 缺陷逃逸率
- 审查覆盖率

### 持续改进

- 对审查流程进行回顾
- 从逃逸的 bug 中学习
- 根据常见问题更新检查清单
- 庆祝高质量的审查和捕捉到的问题
